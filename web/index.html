      AI Dev Center Help

      Learn about the workspace, view the pitch deck, or explore the ADC documentation.

      Start here

      AI Dev Center helps you understand and change a project with an AI team while keeping important actions under your control. It connects analysis, technical planning, development, verification, review and safe delivery in one central workflow instead of leaving you with isolated code suggestions.

      How to use it

      1. Choose an existing project from Projects or add its complete local root.
      2. Describe the outcome you want in Chat.
      3. Watch the current work and any problems in Diagnostic Trace.
      4. Review each approval request before setup, capability use, final acceptance or publishing.

      Projects is your local list of project roots. The Web GUI opens existing projects; greenfield project creation is available through the central workflow path and used by the Real-System E2E test. Each project row has a ... menu. Active projects under Projekte offer Umbenennen (rename the ADC-visible name only; the project's directory, Git remotes and history are never touched) and Archivieren (move the project to the Archiv section above Projekte, shown ABOVE Projekte, without touching its files, its Git repository, or its location on disk). An archived project must first be restored with Wiederherstellen before development can continue on it. Archived projects also offer Löschen, which removes the project from ADC's own project list only — it never deletes the underlying project or repository from disk.

      Diagnostic Trace is the live progress and problem view. At central planning boundaries it presents what kind of input a stage received, which interface and source supplied it, which processor/version handled it, what kind of output it produced, and where that output went. NONE suppresses diagnostic presentation; NORMAL shows essential workflow progress and outcomes; INFO adds concise type/interface and processor identity; VERBOSE adds structured handoffs, engineering fields and safe provider/model context; VERY VERBOSE shows the fullest allowlisted x→f→y projection. At VERY_VERBOSE level, sanitized effective LLM prompts (after template substitution) are visible as diagnostic transparency — raw provider responses, credentials, private model reasoning and executable command payloads remain excluded at every level. NONE only affects presentation — required central audit trace data is preserved.

      Human Approval means the AI can propose a controlled next step, but approval remains a separate decision. Approving one boundary never approves setup, capabilities, Git, publish or hardware actions at another boundary.

      What the AI does

      It first observes the existing project without executing it, preserves its architecture and conventions, clarifies requirements, asks an Engineering Council to compare approaches, and prepares structured work for development and verification. Missing tools are reported rather than silently installed.

      Other frontends and project knowledge

      Web, Signal, API, CLI and MCP are frontends to the same central workflow. Signal transport deployment is not bundled yet. Active Signal chats and projects have a strict 1:1 binding, and chat text cannot switch projects or grant approval.

      Project Intelligence records observed reality. Project Definitions / Memory stores explicit durable decisions and intended rules—not raw chat history. Technical configuration remains in config.yml. Conflicts are shown instead of silently merged.

      Technical and safety details

      The productive Web GUI validates a complete server-local project root and uploads no files. Software, firmware, embedded and hardware-near projects are in scope, but physical hardware actions require their own appropriate approval and are not automatically available.

      Generalized Verification creates a typed, area-aware VerificationPlan from Project Intelligence. For recognised firmware/embedded areas, controlled hardware-free steps are available: ESPHome config validation and compile; PlatformIO build and native hardware-free tests; CMake configure and build. No runner performs flash, upload, OTA, serial monitor or device provisioning. PlatformIO extra_scripts and comparable build-code trust boundaries are detected and reported as unsupported rather than executed automatically. When secure automatic verification is impossible the system reports clearly instead of silently passing.

      A tool_unavailable result remains a structured setup need in the central workflow and never installs anything automatically. Only a command-free SetupPlan materialized from Project Intelligence and the Chairman Council result, followed by separate Setup Human Approval, may invoke a registered structured installer. Availability is checked before and after setup, and only the persisted original VerificationPlan may be retried through the existing Verification architecture. Installation success never grants capability authority.

      Docker is the intended runtime. The core container runs non‑root, without privileged mode and without Docker‑socket or device mounts. The central approval-aware capability registry binds capability and executable identity, allowed operation type, approval provenance, normalized project scope and active registration status. Future toolchain names can be registered without extending a fixed list; today's global registrations are compatibility defaults only. Dynamic registrations are always project-bound, while the same capability may be approved independently for multiple projects. Dynamic registrations follow Project Intelligence → Engineering Council → Chairman approval → Human Approval → controlled capability registration → controlled execution. Registration cannot authorize arbitrary shell commands, argv policies, images, mounts, devices, host access or automatic installation. Denied-argument checks, timeout and output limits remain enforced, and missing tools remain tool_unavailable.

      The central application service opens a capability-specific Human Approval only for metadata present in the actual Project Intelligence and completed Chairman Council result. A matching persisted approval record is required before the existing registry accepts the registration. After restart, only complete approved registrations are restored through the same registry boundary; pending and rejected approvals are not restored. This approval remains separate from setup, Git, publish and physical-hardware approvals.

      Current execution support is deliberately bounded. Hardware flashing, OTA, device activation and other physical hardware actions are not presented as productive capabilities and will require their own separate human approval boundary. A durable Real-System E2E test exercises the full productive central workflow including the Engineering Council, toolchain setup, ESPHome validation/compile, final approval and controlled Git commit with real external provider/model calls; it requires the explicit --real-system-e2e pytest flag and is never part of the normal test suite.

      Typical workflow

      The central process keeps planning, execution and human trust boundaries explicit:

      • Inspect the project, discover and validate requirements, and run preflight checks.
      • Let the Engineering Council evaluate options and materialize a SetupPlan.
      • Require explicit Setup Approval before setup execution.
      • Apply structured development and test changes, run real tests, and review the result.
      • Allow at most one controlled rework before Final Approval.

      After an accepted result, a separate final human approval can mark the run as ready for Git. A further explicit Controlled Git Stage may then create a local commit from validated run-specific whole-file provenance only.

      That local commit only makes the run ready for publish and creates a separate pending Publish Approval. After explicit publish approval, a separate Controlled Publish Stage can push the exact run commit to an existing configured Git remote and explicit branch ref.

      Preexisting or mixed changes, foreign staged content, a final hash mismatch, missing remotes, detached HEAD, unrelated later commits and non-fast-forward pushes are fail-safe blockers. There is no force push or automatic merge/rebase repair. Publish means Git remote push here—not release automation, deployment, hardware flashing or OTA.

      Central Diagnostic Trace

      Each central run has a persistent, ordered diagnostic timeline showing reached phases, actual structured inputs, versioned processor identities and outputs, separate approval boundaries, blockers and Git/publish outcomes such as pending, failed, rework_required, approved, committed and published. ADC entity versions remain distinct from configured provider/model identity. The central request carries the actual Web task into Requirement Discovery alongside—but separate from—observed Project Intelligence, and the trace shows both where the task entered and which internal stage received it.

      Workflow State remains authoritative for decisions, while logging remains intended for developer logs. The Diagnostic Trace observes both but cannot approve setup, Git or publish. Its details are allowlisted and redacted: secrets, raw environments, request headers and full file contents are not stored.

      Safe execution and recovery

      Only one mutating central run can own a project path at a time. Concurrent setup, development, test application, rework, Git or publish requests for the same project are rejected, while read-only planning remains separate.

      If a process stops after mutation began but before a terminal result was saved, the persisted run becomes recovery required. AI Dev Center does not automatically repeat uncertain setup, LLM or file changes. Human approval boundaries remain separate and are never inferred from recovery state.

      The AI team

      • Project Manager – Coordinates the overall task and workflow.
      • Architect – Analyzes project structure and requirements and determines the architectural approach.
      • Developer – Implements the planned changes.
      • Tester – Tests and verifies the implementation.
      • Reviewer – Reviews the result for defects, regressions and quality.

      Important: The user does not manually switch between these roles. The system orchestrates them automatically.

      Use cases

      • Understand an existing project
      • Add a feature
      • Fix a problem
      • Refactor code
      • Open and work with an existing project root
      • Respect existing project files and Git safety boundaries
      • Add tests
      • Review changes
      • Debug the workflow

      Chat and Trace

      The user interacts primarily through Chat. The system shows technical observability in the Trace panel.

      Trace levels: NONE, NORMAL, INFO, VERBOSE, VERY_VERBOSE. These control the diagnostic detail threshold. NONE suppresses presentation without affecting required central audit collection.

      Sensitive values such as secrets, API keys, passwords, prompts, chain-of-thought and sensitive raw arguments are never exposed.
