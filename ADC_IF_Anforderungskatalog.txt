IF-000A — USER / ADAPTER → S1 REQUIREMENT INTELLIGENCE
======================================================================

Boundary:
  External Entry → S1

Producer:
  User / Adapter

Consumer:
  S1 Requirement Intelligence

Primary Artifact:
  CommonRequest / structured user intent

NORMATIVE CONTRACT

IF-000A-REQ-001 MUST:
Die Anfrage MUSS eine strukturierte Request-Identity/Correlation besitzen, die eine
eindeutige Zuordnung über den gesamten ADC-Lauf ermöglicht.

IF-000A-REQ-002 MUST:
Der User Intent MUSS unverändert erhalten bleiben. Der Adapter DARF den Benutzerwunsch
nicht umdeuten, einschränken oder still umformulieren.

IF-000A-REQ-003 MUST:
Die Eingabevalidierung MUSS vor Übergabe an S1 erfolgen. Offensichtlich ungültige,
leere oder strukturell nicht verarbeitbare Eingaben DÜRFEN NICHT still als gültiger
Auftrag an S1 übergeben werden.

IF-000A-REQ-004 MUST NOT:
Der Adapter DARF KEINE technische Lösung auswählen. Die Auswahl einer Toolchain,
Umgebung, Build-Methode oder Engineering-Strategie ist ausschließlich Sache von
S2 Engineering Decision.

IF-000A-REQ-005 MUST NOT:
Der Adapter DARF KEINE Mutation ausführen. Er ist eine reine Eingabeschnittstelle
ohne Projekt-, Target- oder Environment-Mutations-Authority (Current
Implementation Mapping: dies schließt insbesondere Dateisystem-Mutation ein).

IF-000A-REQ-006 MUST:
Die Schnittstelle MUSS technologie-neutral bleiben. Kein Bestandteil der
normativen Anforderungen DARF eine bestimmte Programmiersprache, ein bestimmtes
Framework, ein Build-System oder ein Ecosystem als zentrale Policy voraussetzen.

CURRENT IMPLEMENTATION MAPPING:
Die aktuelle ADC-Implementierung unterstützt verschiedene Entry-Points (CLI,
Web-Interface, API). Die Abbildung auf CommonRequest ist implementationsspezifisch
und KEIN Bestandteil des normativen Contracts.

VERIFICATION MAPPING / CURRENT EVIDENCE:
FUTURE_TEST_NEED: Request-Identity-Erhalt über den gesamten Lauf.
FUTURE_TEST_NEED: User-Intent-Preservation nach Adapter-Pass-Through.
FUTURE_TEST_NEED: Input-Validation verhindert Übergabe ungültiger Requests an S1.
FUTURE_TEST_NEED: Adapter wählt keine technische Lösung (keine S2-Authority-Leak).
FUTURE_TEST_NEED: Technology-Neutrality des Contracts (keine sprachspezifischen Felder).

IF-001 — S1 REQUIREMENT INTELLIGENCE → S2 ENGINEERING DECISION
======================================================================

Boundary:
  S1 → S2.1 / CouncilInput

Producer:
  S1 Requirement Intelligence

Consumer:
  S2 Engineering Decision, zunächst CouncilInput/S2.1

Primary Artifacts:
  RequirementSet / Requirements
  RequirementActivation
  PreflightResult
  Project Intelligence / Project Context
  CouncilInput

NORMATIVE CONTRACT

IF-001-REQ-001 MUST:
Jede bindende Requirement besitzt eine stabile fachliche Identity.

IF-001-REQ-002 MUST:
Requirement ID, Typ, technische Identity, Required-Status und relevante Activation müssen
bis zur S2-Bewertung eindeutig korrelierbar bleiben.

IF-001-REQ-003 MUST:
S2 darf eine Requirement nicht still anhand eines ähnlichen Namens neu erfinden oder ersetzen.

IF-001-REQ-004 MUST:
Eine separate Platform-/Hardware-Angabe darf eine bindende Requirement nur dann erfüllen,
wenn der Contract dies ausdrücklich definiert.

IF-001-REQ-005 MUST:
Activation Provenance muss für blockierende Requirements nachvollziehbar sein.

Soweit im jeweiligen Pfad relevant, muss Activation Provenance strukturell mindestens
folgende Ursprünge unterscheiden:

  a) explizite Benutzer-/Provider-Eingabe (user_input / provider_input),
  b) zentraler Default (central_default),
  c) Fallback aufgrund fehlender Eingabe (fallback_missing_input),
  d) Fallback aufgrund ungültiger Eingabe (fallback_invalid_input),
  e) spätere kontrollierte Transformation (controlled_transformation).

Nicht jede Kategorie muss für jedes Requirement existieren. Die Provenance muss jedoch
für jede Aktivierung, die im jeweiligen Pfad tatsächlich relevant ist, nachvollziehbar
dokumentieren, welcher Ursprung zur Geltung kam.

Activation Provenance ist strukturierte Provenance. Sie darf KEIN rohes Provider-Reasoning
oder Chain-of-Thought enthalten.

IF-001-REQ-005.1 MUST:
Requirement Type bezeichnet generische Architektur-Metadaten (z. B. functional, toolchain,
version, build, test, hardware, security, environment_constraint, project_convention,
approval, verification). Er ist ein strukturiertes, technologie-neutrales
Klassifikationsmerkmal — keine sprach-, framework- oder plattformspezifische Typangabe.

IF-001-REQ-005.2 MUST:
Technical Identity bezeichnet strukturierte, technologie-neutrale Metadaten, über die
ein Requirement, eine Toolchain, eine Plattform oder ein Capability-Ziel
schnittstellenübergreifend unterschieden wird. Sie ist generische Architektur-Metadaten.

(Nicht-normative Beispiele: Eine Requirement könnte Technical Identity "python>=3.10"
tragen; eine Platform-Angabe könnte Technical Identity "arm-none-eabi-gcc" tragen.
Diese Beispiele begründen keine zentrale Policy für ein bestimmtes Ecosystem.)

IF-001-REQ-006 MUST NOT:
S1 darf eine technische Engineering-Lösung auswählen oder Setup ausführen.

FAIL-CLOSED:
ID-Verlust, widersprüchliche bindende Activations oder nicht auflösbare Requirement-Konflikte
dürfen nicht still in einen normalen Council-Handoff übergehen.

DIAGNOSTIC EVIDENCE:
Requirement lineage; Activation provenance; Validierungsresultat; Preflight status.

CURRENT IMPLEMENTATION MAPPING:
app/ai_requirement_discovery.py
app/requirement_validator.py
app/requirement_preflight.py
app/dev_workflow.py CouncilInput-Aufbau

CURRENT EVIDENCE:
SEPARATED_UNITS.
Der aktuelle RSE zeigte für req-c2efb7b8 stabile Identity von Discovery bis CouncilInput,
aber keine vollständige generische S1→S2 productive-chain Evidence.

IF-003 — S2.2 SYNTHESIS → S2.3 ENGINEERING ADMISSIBILITY
======================================================================

Producer:
  S2.2

Consumer:
  S2.3

Artifact:
  finale CouncilResult-Varianten / finale Chairman-Candidates

MUST:
- exakt die finalen Candidates an S2.3 übergeben,
- finale Candidate-IDs erhalten,
- Merge-/Synthesis-Lineage muss die folgende Transformationskette strukturell
  rückverfolgbar machen:
    source Proposal/Candidate identity
    → kontrollierte Synthesis-/Merge-Beziehung
    → finale Chairman-Candidate-Identity,
- relevante Requirement-Referenzen müssen über diese Transformation hinweg
  erhalten bleiben,
- relevante Toolchain-Items strukturiert übergeben,
- Requirement refs, Typ, technische Identity, State und Verification-relevante Felder
  soweit der jeweilige Contract sie benötigt, erhalten.

MUST NOT:
- council_complete=True als technische Zulässigkeit interpretieren,
- originale Agent-Proposals mit finalen Chairman-Candidates gleichsetzen,
- S2.2 eigene technische Zulässigkeitspolitik ausüben.

STRUCTURED REJECTION SUPPORT:
S2.3 muss unterscheiden können zwischen:

PRE-EXECUTION VERIFICATION CONTRACT / STRATEGY ADEQUACY:
- missing reference,
- type mismatch,
- technical identity mismatch,
- semantic mismatch,
- version mismatch,
- verification_contract_gap (die vorgeschlagene Verification-Strategie/der
  Verification-Contract ist für die Bewertung der Zulässigkeit unzureichend;
  zu unterscheiden von fehlender Laufzeit-Verification-Evidence, die zu diesem
  Zeitpunkt noch nicht vorliegen kann),

EXECUTION / MATERIALIZATION ADEQUACY:
- materializability conflict,
- platform constraint.

Die Kategorie "verification_contract_gap" betrifft ausschließlich die
pre-execution-Bewertung der Verification-Strategie. Sie ist explizit zu
unterscheiden von "verification evidence missing", die sich auf tatsächlich
fehlende Laufzeit-Verification-Evidence an einer Schnittstelle bezieht, die
abgeschlossene Verification-Evidence erwartet.

Die Kategorie "Requirement Type" in IF-001-REQ-005.1 ist generische
Architektur-Metadaten — ein strukturiertes, technologie-neutrales
Klassifikationsmerkmal.

Die Kategorie "Technical Identity" in IF-001-REQ-005.2 ist generische
Architektur-Metadaten — strukturierte, technologie-neutrale Metadaten
zur schnittstellenübergreifenden Unterscheidung.

CURRENT IMPLEMENTATION MAPPING:

IF-008 — S3.1 SETUP PLANNING → S3.2 SETUP APPROVAL
======================================================================

Artifact:
  SetupPlan + SetupSteps + SetupEffects

MUST:
- jeder mutierende Step semantisch klassifiziert,
- automatische Executability muss vor Approval auf einen kompatiblen kontrollierten
  Executor-/Capability-Contract abbildbar sein,
- unsupported/manual/already_satisfied/executable ehrlich unterscheiden.

ALREADY_SATISFIED CLASSIFICATION:
Ein SetupStep darf als already_satisfied klassifiziert werden und mutierende
Approval/Execution umgehen, NUR wenn diese Klassifikation durch deterministische,
auditierbare Current-State-Evidence gestützt ist. Kann der geforderte Zustand
nicht nachgewiesen werden, darf der Step NICHT als already_satisfied behandelt
werden.

S3.1 erlangt durch die already_satisfied-Klassifikation KEINE Approval-Authority.
Die menschliche Autorität von S3.2 über geplante Mutation bleibt unverändert.
Ein genuinely non-mutating already_satisfied Step, dessen Zustand deterministisch
belegt ist, benötigt keine Human Approval — er erzeugt keine Mutation.

MUST NOT:
- unstrukturierte, frei formulierte Operationsrepräsentation automatisch mutierbar machen,
- Approval erzeugen,
- Execution durchführen,
- S3.1 darf KEINE Approval-Authority über S3.2 ausüben.

CURRENT IMPLEMENTATION MAPPING:
app/toolchain_materializer.py
Requirement/Setup artifacts in app/requirement_model.py
Ein frei formulierter Shell-Text ist ein aktuelles Beispiel einer
unstrukturierten Operationsrepräsentation, die dieser Regel unterliegt.

  - unsafe paths never mutate outside project.
  resolve_safe_path()

  DeveloperFileApplier

RESTART / PARTIAL-STATE SAFETY:
Wird ein Prozess/Lauf während oder nach S4-Mutation unterbrochen und kann der
Mutationszustand nicht aus Baseline-/Event-Provenance bewiesen werden, MUSS ein
späterer Lauf:

  a) den unsicheren oder partiellen Zustand erkennen,
  b) den aktuellen Zielzustand mit der erfassten Provenance korrelieren,
  c) dieselbe Änderung NICHT still erneut anwenden,
  d) die Änderung NICHT still als erfolgreich behandeln,
  e) fail-closed gehen oder einen kontrollierten Reconciliation-Pfad betreten.

Bestehende Änderungen am Zielzustand (Pre-existing Target Changes) MÜSSEN geschützt bleiben.

ADC DARF NICHT:
- Pre-existing Target State automatisch verwerfen oder überschreiben,
- den Zielzustand destruktiv reparieren.

CURRENT IMPLEMENTATION MAPPING (Konkrete Ausprägungen dieses generischen Verbots):
- zurücksetzen (reset),
- verstauen (stash),
- bereinigen (clean),
- Benutzeränderungen automatisch rückgängig machen,
- dirty files verwerfen,
- automatisch einen "clean state" wiederherstellen.

Diese Semantik MUSS mit Zielbild Abschnitt 17 (Controlled Delivery) kompatibel sein.

IF-026 — S6 LOCAL DELIVERY STATE → PUBLISH APPROVAL / CONTROLLED PUBLISH
======================================================================

NOTE:
This is an unnumbered internal S6 delivery interface because S6 currently has no official S6.x decomposition.

NORMATIVE CONTRACT

MUST:

- publish scope known (wo Publish existiert),
- publish approval distinct from local delivery authority,
- no unrelated pre-existing target state changes included.

Generische Semantik:

mit anderem Delivery-Mechanismus muss diese Grenze mit einem anderen
DeliveryState-Identity-Konzept erfüllen können.

MUST NOT (generisch):
- ADC DARF NICHT automatisch Pre-existing Target State verwerfen oder destruktiv reparieren.

CURRENT IMPLEMENTATION MAPPING — GIT:
In der aktuellen Git-Implementierung:
  - local commit identity known,
  - publish scope known,
  - publish approval distinct from local commit authority,
  - no force push,
  - no unrelated user changes included.

CURRENT EVIDENCE:
Remaining partial area; requires stronger end-to-end approval/provenance evidence.

IF-029 — S6 DELIVERY OUTCOME → USER / PROJECT STATUS / LEARNING
======================================================================

Boundary:
  S6 → Benutzer / Projektstatus / Learning

Producer:
  S6 Delivery & Outcome

Consumer:
  Benutzer / Projektstatus / Learning Memory / FMEA

Primary Artifact:
  Delivery Evidence (Outcome, Delivery State, Publish Evidence wo anwendbar)

NORMATIVE CONTRACT

IF-029-REQ-001 MUST:
Delivery Evidence MUSS dem tatsächlichen Delivery-Outcome entsprechen und
eindeutig attributable bleiben. Der semantische Gehalt (akzeptiertes Outcome,
lokaler Delivery-Zustand, Publish-Zustand wo anwendbar) bleibt erhalten.

IF-029-REQ-002 MUST:
Der Projektstatus MUSS den tatsächlichen Delivery-Zustand reflektieren.
Eine nicht erfolgte oder fehlgeschlagene Delivery DARF NICHT als erfolgreicher
Projektstatus dargestellt werden.

IF-029-REQ-003 MUST:
Learning Memory / FMEA-Updates DÜRFEN NUR auf Basis akzeptierter Evidence erfolgen.
Eine Observation, die nicht akzeptiert wurde, DARF NICHT zu durable Learning werden.

IF-029-REQ-004 MUST NOT:
Diagnostic- oder LLM-Behauptungen allein DÜRFEN KEIN akzeptiertes Learning erzeugen.

IF-029-REQ-005 MUST:
ADC MUSS aus akzeptierter Evidence lernen können, unabhängig vom Publish-Erfolg.
Akzeptierte Evidence aus fehlgeschlagenen Tests, fehlgeschlagenem RSE, abgelehntem
Setup oder anderen nicht-publizierten Outcomes DARF NICHT von Learning/FMEA
ausgeschlossen werden.

Learning Memory / FMEA DÜRFEN NICHT künstlich an eine erfolgreiche Publish-Transaktion
gekoppelt werden. ADC MUSS fähig bleiben, aus akzeptierter Evidence aller Outcome-Klassen
zu lernen — einschließlich gescheiterter Outcomes.

IF-029-REQ-006 MUST:
Die S6→Benutzer-Schnittstelle MUSS technologie-neutral sein. Keine normative
Anforderung DARF ein bestimmtes VCS, eine bestimmte Delivery-Plattform oder ein
bestimmtes Projektmanagement-Tool als zentrale Policy voraussetzen.

CURRENT IMPLEMENTATION MAPPING:
Die aktuelle ADC-Implementierung liefert Delivery-Ergebnisse über Workflow-Resultate
und persistierte Provenance-Daten. Die konkreten Persistenzmechanismen und
Datenstrukturen sind implementationsspezifisch und KEIN Bestandteil des normativen
Contracts.

VERIFICATION MAPPING / CURRENT EVIDENCE:
FUTURE_TEST_NEED: Outcome-Evidence entspricht tatsächlichem Delivery-Zustand.
FUTURE_TEST_NEED: Projektstatus reflektiert realen Delivery-Outcome (nicht fiktiven Erfolg).
FUTURE_TEST_NEED: Learning nur nach akzeptierter Evidence (nicht nach bloßer LLM-Behauptung).
FUTURE_TEST_NEED: Learning aus fehlgeschlagenen Outcomes möglich (keine Publish-Kopplung).
FUTURE_TEST_NEED: Keine Technologie-Spezialisierung im normativen Contract.

IF-027 — DIAGNOSTIC TRACE CROSS-CUTTING CONTRACT
======================================================================

Applies to all relevant IF boundaries.

MUST:
- preserve structured input/output lineage,
- record responsible unit/contract,
- record status/failure category,
- correlate to run,
- retain enough evidence to distinguish producer omission, transition corruption,
  semantic mismatch and valid consumer rejection.

MUST NOT:
- store chain-of-thought,
- store secrets/tokens/credentials,
- rely on truncated raw prompts as the only evidence for structured contracts.

DIAGNOSTIC TRACE / DIAGNOSTIC EVIDENCE MUST NOT:
Diagnostic Trace / Diagnostic Evidence darf NIEMALS formale Entscheidungs-Authority
ersetzen, übersteuern, umgehen oder synthetisieren.

Insbesondere darf Diagnostic Evidence NICHT substituieren für:
  - CandidateValidation (S2.3),
  - Human Engineering Selection (S2.4),
  - Setup Approval (S3.2),
  - Approval Provenance (S3.2),
  - deterministisches VerificationResult (S5.2/S5.3),
  - Final Approval (S5→S6),
  - Publish Approval (S6).

Diagnostic Evidence ist Evidence, nicht Authority.

Special target requirements (referenziert konsistent IF-001-REQ-005):
- Activation Provenance mit strukturierten Ursprüngen (user_input, central_default,
  fallback_missing_input, fallback_invalid_input, controlled_transformation),
  soweit im jeweiligen Pfad relevant,
- Final Candidate Snapshot,
- Transformation/Merge Provenance,
- Structured CandidateValidation verdicts,
- Verification target/capability rejection categories.
